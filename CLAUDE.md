# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Scala 3 client library for the [Warp10](https://www.warp10.io/) geo/time series database, built on Pekko HTTP / Pekko Streams and circe. Published to Maven Central as `com.clever-cloud %% warp10-scala-client`. Single sbt module, no subprojects.

## Commands

```bash
sbt compile
sbt test                                                  # full suite, needs Docker (see below)
sbt "testOnly GTSSpec"                                    # specs in the default package
sbt "testOnly com.clevercloud.warp10client.Warp10StackTest"
sbt "testOnly Warp10ClientSpec -- ex \"fetch success\""   # filter specs2 examples by name
sbt githubWorkflowGenerate                                # regenerate .github/workflows after build.sbt changes
sbt ghpagesPushSite                                       # publish scaladoc to gh-pages
```

- `Warp10ClientSpec` starts a real Warp10 container through `testcontainers-scala-warp10` (image tag pinned in `Warp10TestContainer`), so Docker must be running. It also binds `MockServer` on `localhost:8888`. `GTSSpec` and `Warp10StackTest` are pure and run without Docker.
- With a recent Docker daemon (29+), the bundled testcontainers client is rejected ("client version 1.32 is too old", reported as "Could not find a valid Docker environment"). Run `sbt -Dapi.version=1.44 test` to work around it.
- CI runs on JDK 21; use the same locally (`JAVA_HOME`) if the default JDK is newer.
- The build's git plugin fails inside a `git worktree` (`NoWorkTreeException`); use a plain clone for a second checkout.
- Tests run sequentially (`Test / parallelExecution := false`).
- There is no sbt scalafmt plugin; `.scalafmt.conf` (scalafmt 3.7.13, `maxColumn = 120`) is applied by Scala Steward / the standalone CLI. Not all files are currently formatted, so avoid reformatting unrelated code.

## CI and release

- `.github/workflows/*.yml` are generated by `sbt-github-actions` from the `githubWorkflow*` settings in `build.sbt`. Never edit them by hand: CI runs `sbt githubWorkflowCheck` and fails if they are out of sync. Change `build.sbt`, then run `sbt githubWorkflowGenerate`.
- Publishing to Maven Central happens on `v*` tags via `sbt ci-release`. The version is hard-coded in `build.sbt` (`ThisBuild / version`), so bump it there before tagging.

## Architecture

Everything lives in `src/main/scala/com/clevercloud/warp10client`.

**Entry points.** `object WarpClient` (in `Warp10Client.scala`) is the factory; `class Warp10Client` is the API. The README shows `Warp10Client(host, port)`, but the actual call is `WarpClient(host, port, scheme)` with implicit `WarpConfiguration`, `ActorSystem` and `Materializer` in scope. `WarpConfiguration(baseUrl)` derives the three endpoints: `/api/v0/update`, `/api/v0/fetch`, `/api/v0/exec`.

**Context and HTTP pool.** `WarpClientContext` (in `WarpClientUtils.scala`) bundles the configuration, the materializer and a `PoolClientFlow = Flow[(HttpRequest, UUID), (Try[HttpResponse], UUID), ?]`, and re-exposes them as implicits (`import warpClientContext._`). In production the flow is a Pekko `cachedHostConnectionPool[UUID]`. Because the pool flow is injectable, tests build a `WarpClientContext` with a hand-written `Flow` that pattern-matches on the request body and returns canned responses — this is the preferred way to unit test request serialization and response handling without a server.

**One object per endpoint**, each exposing a Pekko Streams `Flow` that follows the same shape: build `HttpRequest` → tag with a per-flow `UUID` → `via(poolClientFlow)` → filter on that UUID → process the response.

- `Pusher` — `Flow[GTS, …]` / `Flow[Seq[GTS], …]`, POSTs the Warp10 text input format (`GTS.serialize`).
- `Fetcher` — `Flow[Query[FetchRange], …]`, GETs with `format=text` and parses the body with `GTS.parse`.
- `Runner` — `Flow[WarpScript, String, …]` for `/exec`, then `jsonToGTSSeq()` (decodes the JSON GTS output format) or `jsonToStack()` (wraps the raw JSON stack in `Warp10Stack` for typed access via circe `Decoder`s).

`Warp10Client` exposes each of these twice: as a `Flow` for stream composition, and as a `Future`-returning convenience overload that runs a `Source.single(...)` through the flow.

**Error handling is not uniform across endpoints** — keep this in mind when changing or adding API:

- `push` / `fetch` return `Future[Either[WarpException, A]]`; HTTP errors become `Left`. (A GTS parse failure in `Fetcher` still throws, i.e. a failed `Future`.)
- `exec` / `execStack` return bare `Seq[GTS]` / `Warp10Stack` and signal errors by throwing `WarpException`, failing the stream/`Future`. On HTTP 500, `Runner` reads the `X-Warp10-Error-Message` and `X-Warp10-Error-Line` headers (falling back to the HTML body) and fills `WarpException.line`.

**Models (`models/`).**

- `gts_module.scala` — everything is nested in `object gts_module`, so users and tests import `models.gts_module._`. Holds `GTS`, `GTSPoint`, `Coordinates`, the `GTSValue` hierarchy (long/double/boolean/string/macro values), their text serialization and parsers, and the `gts_errors` ADT (`InvalidGTSFormat` …) returned as `Left` by the parsers. Parsing a macro value is intentionally not implemented.
- `Query.scala` — `Query(selector, range, dedup)` plus the `Selector` and `FetchRange` ADTs; each `serialize`s to its fetch query-string fragment. `FetchRange.apply` is overloaded on argument types to pick the variant (start/stop, now+timespan, now+count, micros). Label selector keys carry the operator as a suffix (`"label=" -> "exact"`, `"label~" -> "regex.*"`).

Note that Warp10 timestamps are in microseconds throughout (see the `…000` / `toMicros` conversions in `Query.scala`).
